## Issuing a new certificate

```sh
aster-acme cert issue -n example-cert -a default \
  -d example.com -d '*.example.com' \
  -c dns_provider --provider cf-prod
```

- `-n/--name`: the long-lived managed certificate name. Defaults to the first normalized identifier plus a random suffix (IP primaries get an `ip-` prefix); an explicitly requested existing name is rejected
- `-a/--account`: the issuing account
- `-d/--domain`: DNS names, repeatable; wildcards are written `*.example.com` and require DNS validation
- `--ip`: IP addresses (RFC 8738), repeatable; requires HTTP-01/TLS-ALPN-01, the primary identifier is the first `-d`, else the first `--ip`
- `--profile`: CA certificate profile (draft-ietf-acme-profiles); `account show --profiles` lists the advertisement, `account update --profile` sets an account default, explicit flags win. Let's Encrypt IP issuance requires `shortlived`
- `--chain CHAIN`: use a matching candidate for this issuance only; no preference is saved. `CHAIN` is the candidate's top-most certificate RFC 4514 distinguished name, or its common name (for example, `CN=ISRG Root X1,O=Internet Security Research Group,C=US` or `ISRG Root X1`). If unavailable, the issued operation remains resumable with `--resume`
- `--preferred-chain CHAIN`: use a matching candidate now and save it as a soft preference; `CHAIN` accepts the same RFC 4514 distinguished name or common name forms. Future operations fall back to the CA default with a warning when unavailable
- `--default-chain`: follow the CA default for this issuance without changing an existing preference

**Chain selection**: the CA advertises same-leaf candidate chains through `Link; rel="alternate"` on the download response. Interactive issuance first selects the chain for this issuance; choosing a concrete chain then asks whether to save it as a soft preference (default No). The first menu item follows the CA default without changing a saved preference. Noninteractive callers use `--chain` for a one-time choice, `--preferred-chain` for a saved soft preference, or `--default-chain` to follow the default without changing an existing preference. An unavailable soft preference falls back to the CA default with a warning; an unavailable one-time choice leaves the issued operation resumable, without creating a new order. `cert show` displays the saved preference and the published chain’s DN and fingerprint.
- `-c/--challenge`: the validation implementation — see [Validation Methods](/en/using/challenges/)
- `-k/--key-type`: certificate public key algorithm, ecdsa-p256 by default; also ecdsa-p384/p521, ed25519, rsa-2048/3072/4096/8192. If the CA rejects the choice, the actual error is preserved — AsterACME never retries with a different algorithm

Each generation gets fixed keys and a fixed CSR: recovery never generates replacement material, and renewal reuses the same identifiers, account, and algorithm. Keys and CSRs are generated before any CA request, so cancelling the interactive flow leaves no half-initialized identity.

**Similar-order protection**: when a new request has no explicit name and an unfinished candidate with a fully matching definition exists, the terminal offers to resume or create fresh; scripts fail with the exact resume command instead of silently duplicating the order.

## Interrupted recovery

Every step of issuance — intents, order URLs, validation material, final artifacts — is persisted before it is advanced. Network timeouts, cancellation, timeouts, and exhausted polling all leave the application at its checkpoint:

```sh
aster-acme cert issue --resume example-cert
aster-acme cert issue --resume example-cert --operation FULL-OPERATION-ID
```

- `--resume [NAME]`: the terminal lists unfinished applications when the name is omitted; scripts must pass a name or a full `--operation`
- Completed generations never participate in resume selection
- Manual validations (manual_dns/manual_http) re-display the pending material on resume; `--yes` only confirms after the material has been shown — unseen material is never accepted as published
- Orders that reached terminal failure (invalid) no longer participate in recovery; inspect the error details with `cert show`

**Uncertain outcomes are not replayed**: for example, if the response to order creation is lost, AsterACME keeps the "creation uncertain" state rather than blindly placing another order; recovery reconciles against the saved evidence.

## Inspecting certificates

```sh
aster-acme cert list
aster-acme cert list --history
aster-acme cert show example-cert
aster-acme cert show example-cert --history
aster-acme cert show example-cert --verify
aster-acme cert show --operation OPERATION-ID
```

`list` shows one row per managed certificate by default; `--history` expands all generations. `show` displays the current in-use generation: identifiers, validity, validation method, deployment bindings, revocation state, and the renewal plan. Everything is offline by default; `--verify` queries the CA for the order and authorizations — it does not imply revocation status was checked, nor OCSP/CRL.

Time fields distinguish **order status** from **certificate expiry**; the NEXT RENEWAL column comes from the renewal plan (see [Renewal and ARI](/en/using/renewal/)).

## Cleaning up failed applications

```sh
aster-acme cert remove example-cert --failed --yes
```

`--failed` removes only **clearly failed, unrecoverable** unfinished applications: order creation explicitly rejected with 4xx by the CA, the fixed CSR rejected (badCSR), terminal order/authorization states, and expired orders. Applications with network timeouts, 408/429 rate limiting, or unknown outcomes are kept. The command never touches the CA, never cleans DNS or webroot material on its own, and preserves issued generations.

## Debug diagnostics

```sh
aster-acme cert issue --resume example-cert --yes --debug
```

`--debug` enables safe DEBUG-level logging: checkpoint phases, order-intent persistence, request categories, HTTP status and durations, nonce retry sequences. It **never** logs private keys, CSR/JWS bodies, response bodies, or URLs carrying credentials. Diagnostics are suppressed in JSON mode; drop `--json` when you need human-readable diagnostics.
